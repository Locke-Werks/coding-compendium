## More

Open almost any project and the same shape appears, whatever language it is written in.

```text
my-app\
  src\              the code people wrote
  tests\            the code that checks the other code
  docs\             prose, if the project has any
  dist\             generated output, never edited by hand
  node_modules\     downloaded dependencies, never edited by hand
  .git\             the repository itself
  .gitignore        the list of what git skips
  README.md         start here
  package.json      the manifest: name, dependencies, scripts
```

Three categories, and knowing which is which answers most questions you will have about a
folder you did not create.

**Written by people.** `src`, `tests`, `docs`, the manifest, the readme. These are committed,
reviewed, and the only ones worth reading.

**Generated by the build.** `dist`, `build`, `target`, `out`, `bin`, `obj`, `.next`,
`__pycache__`. Nothing here was typed by a person. All of it is reproducible from the source,
which is why it is git-ignored ([d12](#d12-gitignore-and-what-not-to-commit)) and why
deleting it costs you a rebuild and nothing else ([i3](#i3-builds-and-artifacts)).

**Downloaded.** `node_modules`, `vendor`, `.venv`, `~\.cargo`. Someone else's code, fetched
by the package manager from the lockfile. Also git-ignored, also disposable, also not worth
reading ([g1](#g1-what-a-dependency-is)).

The single most useful habit here: when a folder confuses you, check whether it appears in
`.gitignore`. If it does, the project itself is telling you the folder is disposable and
nobody wrote it by hand.

The entry point, meaning the file where execution starts, is nearly always in `src` and
nearly always named for what it is: `main.rs`, `main.py`, `index.ts`, `Program.cs`. The
manifest names it when the convention does not ([c3](#c3-what-running-means)).

## Full

### The same folder, one ecosystem at a time

| Ecosystem | Source | Entry point | Build output | Dependencies |
|---|---|---|---|---|
| Rust | `src\` | `src\main.rs` or `src\lib.rs` | `target\` | `~\.cargo\registry` |
| Node | `src\` | `src\index.ts` | `dist\` or `build\` | `node_modules\` |
| Python | `src\<package>\` | `main.py` or `__main__.py` | `dist\` | `.venv\` |
| C# | `src\` | `Program.cs` | `bin\` and `obj\` | `~\.nuget` |
| Java | `src\main\java\` | A class with a `main` method | `target\` or `build\` | `~\.m2` |

Java's `src\main\java\com\company\project\` is not a mistake and not optional: the folder
path has to match the package name, so the depth is the language's requirement rather than
somebody's taste.

### The dot files and folders at the root

Anything starting with a dot is configuration or tooling. Windows Explorer shows them,
which is a small mercy. The ones you will actually meet:

| Name | What it is | Yours to edit |
|---|---|---|
| `.git\` | The entire repository, including every commit | Never by hand |
| `.gitignore` | Patterns git will not offer to track ([.gitignore](#gitignore)) | Yes |
| `.github\workflows\` | What runs automatically when you push ([h5](#h5-ci-cd)) | Yes |
| `.vscode\` | Editor settings shared with the project | Yes |
| `.env` | Local secrets and settings, never committed | Yes |
| `.env.example` | The same file with the values removed, committed on purpose | Yes |
| `.editorconfig` | Indentation and line ending rules your editor obeys | Rarely |
| `.claude\` | Agent settings and project instructions ([e4](#e4-claude-md-and-agents-md)) | Yes |
| `.venv\` | A Python environment ([g4](#g4-environments-and-isolation)) | Never by hand |

`.env.example` is worth pausing on. It exists so that a new person can copy it to `.env` and
fill in their own values, which is how a project tells you which secrets it needs without
handing you any.

### Which folders are safe to delete

In order, from certainly safe to certainly not:

1. **Build output.** `dist`, `build`, `target`, `out`, `.next`, `__pycache__`. Deleting
   costs one rebuild.
2. **Downloaded dependencies.** `node_modules`, `.venv`, `vendor`. Deleting costs one
   install, and it is the standard fix when dependencies get into an impossible state.
3. **Caches.** Anything with `cache` in the name, and `.turbo`, `.parcel-cache`,
   `.pytest_cache`. Deleting costs a slower next run.
4. **Log folders.** Usually `logs`. Read them first ([f4](#f4-logs)).
5. **Everything else.** Not safe. `src`, `tests`, the manifest, the lockfile, and `.git` are
   the project.

The general rule, stated once: if it is in `.gitignore` and the tool that made it still
exists, it can be deleted. `.git` is the exception, because it is not in `.gitignore` and
deleting it destroys the entire history while leaving the files behind.

### Where the tests live

Two conventions, and projects rarely mix them:

- **A `tests` folder beside `src`.** Rust integration tests, Python, and most Node projects.
- **Test files sitting next to the code they test**, named `thing.test.ts`, `thing_test.go`,
  or `test_thing.py`. Go and many React projects work this way, and Rust puts unit tests in
  the same file as the code inside a `mod tests` block.

Finding the tests is step four of walking into an unfamiliar project
([j4](#j4-reading-a-repo-you-did-not-write)), because they are the most honest description
of what the code is supposed to do.

### Monorepos, and why the shape suddenly looks wrong

A monorepo holds several projects in one repository. The tell is a top-level `packages\` or
`apps\` folder with a manifest in each subfolder as well as one at the root.

```text
my-company\
  package.json          the workspace root, lists the members
  pnpm-workspace.yaml
  apps\
    web\                a project, with its own package.json
    api\                another one
  packages\
    ui\                 shared code both apps import
```

The thing to know before running anything: commands run from the root usually apply to every
member at once, and commands run from inside one folder apply to that member. When a build
command does nothing or builds far too much, check which folder you are standing in.

### The layout of this app, annotated

```text
content\      the cards, as Markdown files. The actual product.
schema\       JSON Schemas the cards are validated against.
tools\lint\   the linter that checks every card before it merges.
src\          the front end, TypeScript and React.
src-tauri\    the Rust side, and the Windows installer configuration.
dist\         generated. The built front end.
build\        generated.
node_modules\ downloaded.
```

Four folders written by people, three that regenerate. That ratio is normal, and it is why a
repository that looks enormous in Explorer is usually much smaller than it appears.
