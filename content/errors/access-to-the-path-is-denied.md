---
id: access-to-the-path-is-denied
title: "Access to the path 'C:\\...' is denied"
type: error
verified: 2026-08-02
volatility: low

category: permission

# Shows the access rules on the file or folder. Look for your own username in
# the list and what it is allowed to do.
verify: Get-Acl .\<file> | Format-List

sample: |
  Remove-Item : Access to the path 'C:\Users\you\dev\scraper\dist\app.exe' is denied.
  At line:1 char:1
  + Remove-Item .\dist -Recurse -Force
  + ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
      + CategoryInfo          : PermissionDenied: (C:\Users\you\...\dist\app.exe:FileInfo) [Remove-Item], UnauthorizedAccessException
      + FullyQualifiedErrorId : RemoveFileSystemItemUnAuthorizedAccess,Microsoft.PowerShell.Commands.RemoveItemCommand

patterns:
  - "Access to the path"
  - "is denied"
  - "UnauthorizedAccessException"

means: >
  Windows refused to let this program read, write, or delete that file. Refusal comes from
  one of three places. The file is marked read-only. The file belongs to somewhere your
  account has no rights, such as `C:\Program Files`. Or another running program has the
  file open and Windows will not let two things change it at once. The third case is the
  most common one during development and it does not look like a permission problem at
  all.

danger: >
  Two steps below delete files. `Remove-Item -Recurse -Force` deletes a folder and
  everything inside it with no recycle bin and no undo. Only aim it at build output such
  as `dist`, `target`, `build`, or `node_modules`, all of which are regenerated by
  rebuilding. Never aim it at a source folder.

fix_ladder:
  - try: Close whatever has the file open, then run the command again.
    why: >
      Assumes another program is holding the file. A running dev server, a debugger, an
      editor with the file open, or a previous run of your own program that never exited
      all do this. Windows locks harder than macOS or Linux here, so this is the first
      thing to suspect and it costs nothing.

  - try: Find out which process is holding it.
    command: Get-Process | Where-Object { $_.Modules.FileName -like "*<filename>*" }
    shell: powershell
    why: >
      Assumes something is holding the file and you cannot tell what. This lists processes
      that have the file loaded. Resource Monitor does the same job with a search box:
      press the Windows key, type `Resource Monitor`, open the CPU tab, and use the
      Associated Handles search.

  - try: Clear the read-only attribute.
    command: Get-ChildItem .\<folder> -Recurse | ForEach-Object { $_.IsReadOnly = $false }
    shell: powershell
    why: >
      Assumes the file is marked read-only. Files that arrived from a zip, a network share,
      or another user's account often carry the flag. The flag survives copying, so a whole
      folder can be affected at once.

  - try: Check whether the path is somewhere your account owns.
    command: Get-Acl .\<file> | Format-List
    shell: powershell
    why: >
      Assumes the location itself is protected. Anything under `C:\Program Files`,
      `C:\Windows`, or another user's folder needs an administrator window. Anything under
      `C:\Users\<yourname>\` does not, and if you are hitting this inside your own folder
      the cause is a lock or a read-only flag rather than ownership.

  - try: Open PowerShell as administrator and run it there.
    why: >
      Assumes the operation genuinely needs elevated rights. Right-click the PowerShell
      entry in the Start menu and pick Run as administrator. Use this last, because it
      makes the command succeed without telling you why it was failing, and a build that
      needs administrator rights to clean up is usually a bug worth fixing.

if_none_worked: >
  Paste the full error including the `CategoryInfo` line, the exact command, and the output
  of `Get-Acl` on the path. Also say whether the path is under `C:\Users\<yourname>\` or
  somewhere else. That location detail is what people summarize away, and it decides
  whether this is a lock, a flag, or genuinely a rights problem.

The wording points at permissions, and during development the cause is usually a lock.

Build tools hit this constantly. A dev server is still running and holding a file in
`dist`. A previous test run left a process alive. An editor has a file open with an
exclusive handle. The build then tries to delete the folder and Windows says no.

Antivirus is the other repeat offender. Real-time scanning opens a file the instant it is
written, which is often the same instant your build tries to move or rename it. If the
same command fails at random and succeeds on the second try, that pattern is the
signature.

Running as administrator makes the message go away without answering the question. Try it
last, and treat needing it as information rather than as a fix.
